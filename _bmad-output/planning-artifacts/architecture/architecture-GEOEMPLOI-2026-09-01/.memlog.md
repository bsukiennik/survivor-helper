- (decision) [ADOPTED] Paradigm: hexagonal (ports & adapters). Core = pure business logic (job matching, catch/application integrity, moderation, account governance rules), no framework/infra concerns inside it. Source: PRD addendum, brainstorming + PRD Discovery sessions.
- (decision) [ADOPTED] Two adapters designed first: Persistence (DB) and Mapping (tile provider + server-side cache) - both must support a local/self-hosted swap per sovereignty constraint (PRD §8).
- (constraint) Sovereignty boundary: no adapter may call a paid/proprietary third-party service (no managed DB, no managed object storage, no commercial map/auth/email API, no AWS/GCP/Azure). Every external dependency must be self-hostable and run fully local from a fresh clone.
- (decision) Frontend/Backend split: SPA (Vite+React, client-side rendered) consuming a documented REST API from NestJS - no SSR, no BFF layer. Frontend never calls the map tile provider directly (goes through the Mapping adapter's cache endpoint).
- (decision) Auth: JWT issued and verified by the NestJS backend itself (no third-party auth provider, per sovereignty). Bearer token in Authorization header; no server-side session store needed.
- (decision) Real-time delivery: a 'Listing Feed' port with two adapters - WebSocket (default) and Polling - selected by config (env var), not code change. Both adapters implement the identical port interface so behavior at the port boundary is guaranteed consistent; WS can also be fully disabled by config. Client dedupes delivered Listings by ID regardless of active adapter.
- (decision) Catch/Application integrity lives in the domain layer, not in a controller or the DB alone: a service-level 'ApplyToListing' use case enforces the (JobSeeker,Listing) uniqueness rule and computes/persists the catch count inside one transaction, so no adapter or client can bypass it. DB carries a matching UNIQUE(job_seeker_id, listing_id) constraint as a second line of defense, not the primary enforcement point.
- (decision) RGPD erasure: account deletion is a single domain use case (AccountDeletion) that anonymizes personal fields and enforces the bounded legitimate-interest exception (PRD FR-21) - no adapter or repository may issue a raw personal-data delete/anonymize outside this use case.
- (decision) Brand compliance: a single design-token layer (colors/typography) sourced from the ministerial charter constants, consumed by every screen/component - no component hardcodes the institutional blue or picks its own font. Display name 'GéoEmploi' lives in one i18n/strings source, never inlined.
- (version) Frontend: React 19.2.8, Vite 8.0.9, TypeScript (pinned conservatively - see Deferred), Tailwind CSS 4.3.3, shadcn/ui (CLI-copied components, no fixed version to pin)
- (version) Backend: NestJS 12.0.1, class-validator + class-transformer, Drizzle ORM ~0.44.x (latest pre-1.0 stable; 1.0.0-beta exists but not GA - do not adopt beta)
- (version) Database: PostgreSQL 18.6, self-hosted via Docker Compose (satisfies sovereignty - not a managed service)
- (assumption) WebSocket adapter implementation: NestJS's built-in @nestjs/websockets gateway with the 'ws' library (not socket.io) - lighter weight, sufficient for a simple broadcast use case. [ASSUMPTION - team can swap to socket.io without violating the Listing Feed port contract]
- (assumption) Tile cache implementation: in-process LRU + filesystem cache inside the NestJS backend (no Redis) for v1 - avoids extra infra for a 2-week local-run project. [ASSUMPTION - Redis is a documented scale-up path under Deferred, not required now]
- (question) NestJS 12 (released 2026-08-27) and TypeScript 7.0 (native Go compiler, released 2026-08-05) are both very recently GA - ecosystem compatibility (decorator metadata, class-validator, ts-node/tooling) not yet battle-tested at time of writing. Flagged for the version-verification reviewer lens.
- (version) TypeScript 6.0.3 pinned - deliberately NOT the newly-released TypeScript 7.0.2 (Go-native compiler, released 2026-08-05, ~4 weeks old at authoring time). 6.0.3 is the last JS-codebase release and a stabilization milestone; decorator-heavy NestJS 12 + class-validator code is a much better-tested combination against it than against a brand-new compiler rewrite, which matters more than raw speed for a 2-week deadline. [ASSUMPTION - revisit if TS7 ecosystem compat matures]
- (decision) Naming convention: domain entities use Glossary terms verbatim (Listing, Application, JobSeeker, Employer, Administrator, SubscriptionTier, Report, Badge); DB tables snake_case plural; all entity IDs are UUIDv4; DTOs PascalCase+Dto suffix, domain events PascalCase+Event suffix.
- (decision) Data & format convention: dates ISO8601 UTC; error responses follow NestJS's standard exception-filter shape (statusCode, message, error, timestamp, path); monetary values (SubscriptionTier pricing) stored as integer cents, never floats.
- (decision) State/cross-cutting convention: all persistence mutation goes through the domain/service layer - controllers and adapters never call the repository directly. Config is env-var based, validated at process boot (fail fast on a missing required var, matching .env.example). Structured JSON logging; Catch/Application-creation events carry an explicit audit log line (job seeker id, listing id, timestamp) per PRD FR-7.
- (decision) Deployment & environments: single environment for this engagement - fully local via Docker Compose (Postgres 18.6 container + NestJS backend + Vite dev/preview frontend). No cloud/staging/production environment exists or is provisioned; the PRD's one-page deployment note (§8) covers the hypothetical production shape separately from this spine.
- (decision) Structural seed: monorepo with apps/frontend (Vite+React) and apps/backend (NestJS, hexagonal layout: domain/ - entities+use-cases, application/ - ports, infrastructure/ - adapters (persistence, mapping, realtime), interfaces/ - REST controllers+WS gateway).
- (decision) Capability -> Architecture map: features 4.1-4.3 (map discovery, profile, gamified catch) -> frontend map module + backend Listing/Application domain services, governed by AD hexagonal-core + Catch-integrity AD. Features 4.4-4.7 (employer account, publication, application mgmt, dashboard) -> backend Employer/Listing services + frontend employer dashboard module. Feature 4.8 (live updates) -> Listing Feed port (AD real-time). Features 4.9-4.11 (moderation, governance, metrics) -> backend Admin module + RGPD erasure use case. Feature 4.12 (brand/naming) -> shared design-token layer + i18n strings source, governs all frontend modules.
